%% =================== ABSTRACT ======================================
\begin{abstract}
Water scarcity in rural agricultural landscapes necessitates scientific, data-driven planning for surface water harvesting structures. This report presents the technical design, mathematical foundation, system architecture, and verification results of the \textbf{AI-based Village Pond Planning System} (JalSetu Studio). The system integrates satellite map visualization, contour/DEM terrain analysis, automated boundary geocoding, and historical rainfall integration to recommend optimal pond siting and excavation parameters. A high-performance web architecture was constructed featuring a vanilla JavaScript/Leaflet interactive frontend, an Nginx load balancer operating across three FastAPI backend VM instances (\texttt{10.1.75.52}, \texttt{10.1.75.53}, \texttt{10.1.75.54}), and a two-level caching engine (in-memory LRU coupled with Supabase PostgreSQL persistence). Hydrological modeling leverages coupled USDA Soil Conservation Service Curve Number (SCS-CN) runoff yield modeling, D8 steepest-descent flow direction routing, and recursive upstream Breadth-First Search (BFS) watershed catchment delineation. Pond geometry is optimized using a 3D inverted trapezoidal frustum model ($1.5:1$ side slope ratio) with $+0.5\text{ m}$ freeboard allowance. Empirical testing demonstrates response times under $200\text{ ms}$ for cached queries and $1.84\text{ s}$ for fresh terrain analyses, with $100\%$ pass rates across the automated 33-test suite. The complete application is deployed on the lab cluster at \url{http://10.1.75.51:4218/ui/}.
\end{abstract}

\keywords{Village Pond Planning, Geospatial Analysis, Rainwater Harvesting, Catchment Estimation, Web GIS, REST APIs, Load Balancing, SCS-CN Model}

\section{Introduction}
\label{sec:intro}
Rural agricultural security in arid and semi-arid regions relies heavily on community and farm ponds that capture seasonal monsoon runoff for dry-season irrigation, groundwater recharge, and livestock consumption. Traditional pond site selection relies primarily on visual inspection or local intuition, often leading to sub-optimal placement in flat zones with insufficient catchment yield, excessive evaporation losses, or embankment instability. 

This report documents the design and implementation of the \textbf{AI-based Village Pond Planning System}, an end-to-end geospatial web application developed for CSD Assignment 1. The application automates the full engineering pipeline: from satellite-assisted village search and polygon land selection, to digital elevation interpolation, historical rainfall aggregation, D8 watershed catchment delineation, SCS-CN runoff volume estimation, and 3D frustum pond sizing optimization. The remainder of this report is organized as follows: Section~\ref{sec:requirements} defines functional and non-functional requirements; Section~\ref{sec:architecture} details system architecture and technology choices; Section~\ref{sec:methodology} presents the mathematical and algorithmic methodology; Section~\ref{sec:implementation} outlines backend, frontend, and database implementation; Section~\ref{sec:csd-themes} explicitly maps core Computer System Design (CSD) concepts; Section~\ref{sec:results} evaluates performance and accuracy; Section~\ref{sec:discussion} reflects on limitations; Section~\ref{sec:ai-usage} declares AI tool usage; and Appendix~\ref{sec:appendix} provides repository details.

\subsection{Motivation}
Manual selection of village pond sites presents significant engineering challenges due to:
\begin{enumerate}[leftmargin=*]
    \item \textbf{Micro-Topographic Complexity}: Identifying natural terrain depressions and flow pathways across large agricultural land areas is error-prone without Digital Elevation Models (DEMs).
    \item \textbf{Data Fragmentation}: Historical rainfall records, soil retention coefficients, and elevation datasets are isolated across different agency databases.
    \item \textbf{Civil Engineering Calculations}: Manual calculation of slope stability, runoff yield, and 3D excavation volumes requires specialized GIS software inaccessible to village panchayats and local agricultural officers.
\end{enumerate}
An automated, browser-accessible decision-support tool empowers non-expert stakeholders to select land areas interactively and receive instantaneous, mathematically sound siting and sizing recommendations.

\subsection{Scope of the Project}
The system scope includes:
\begin{itemize}
    \item Interactive satellite/street map display with OpenStreetMap Nominatim village search and automated boundary polygon fetching.
    \item Interactive user tools to draw freehand lasso or rectangular land polygons on the map.
    \item Automated fetching/interpolation of DEM elevation matrices and historical 10-year monthly precipitation records (Open-Meteo API).
    \item D8 steepest-descent flow direction calculation and recursive upstream BFS catchment delineation.
    \item SCS-CN surface runoff volume estimation and 3D inverted trapezoidal frustum pond sizing ($1.5:1$ side slope, $+0.5\text{ m}$ freeboard).
    \item Single-step KML/KMZ contour map upload analysis endpoint (\texttt{/analyzeContour}).
    \item Nginx load balancing across three backend server instances with two-level caching.
\end{itemize}
\textbf{Out of Scope}: Detailed soil mechanical cohesion/shear strength testing, structural civil engineering modeling of concrete spillways, and real-time land ownership ledger verification.

\section{Methodology}
\label{sec:methodology}

\subsection{Terrain and Elevation Analysis}
Terrain elevation is modeled as a discrete 2D grid matrix $Z \in \mathbb{R}^{M \times N}$. For user-selected bounding boxes or KML contour uploads, elevation values are obtained via SRTM 30m raster tiles or interpolated from KML polyline coordinates using Delaunay triangulation. For arbitrary continuous geographic coordinates $(\text{lat}, \text{lon})$, smooth elevation estimation is performed via bilinear interpolation from the bounding grid cell coordinates $(x_0, y_0), (x_1, y_1)$:
\begin{equation}
z(x, y) = \frac{(x_1 - x)(y_1 - y)}{(x_1 - x_0)(y_1 - y_0)} z_{00} + \frac{(x - x_0)(y_1 - y)}{(x_1 - x_0)(y_1 - y_0)} z_{10} + \frac{(x_1 - x)(y - y_0)}{(x_1 - x_0)(y_1 - y_0)} z_{01} + \frac{(x - x_0)(y - y_0)}{(x_1 - x_0)(y_1 - y_0)} z_{11}
\end{equation}

Local ground slope percentage $S_{i,j}$ is derived using 3x3 Sobel spatial gradient filters:
\begin{equation}
G_x = \frac{\partial z}{\partial x}, \quad G_y = \frac{\partial z}{\partial y}, \quad S_{i,j} = \sqrt{G_x^2 + G_y^2} \times 100\%
\end{equation}
Candidate pour-points are identified by filtering for local elevation minima where slope $S_{i,j} \le 6.0\%$.

\subsection{Catchment Area Delineation}
The hydrological contributing basin for a candidate pour-point $(r_0, c_0)$ is computed using D8 (Eight-Direction) steepest descent flow routing. For each cell $(r, c)$, flow direction $D(r,c) \in \{1, 2, 4, 8, 16, 32, 64, 128\}$ is assigned to the neighbor with maximum downward gradient:
\begin{equation}
\Delta z_k = \frac{z(r, c) - z(r + \Delta r_k, c + \Delta c_k)}{d_k}
\end{equation}
where $d_k = 1.0$ for cardinal directions and $d_k = \sqrt{2}$ for diagonal directions. Catchment delineation is executed via recursive upstream Breadth-First Search (BFS) starting from $(r_0, c_0)$, collecting all grid cells whose flow path terminates at the pour-point:
\begin{equation}
\text{Catchment}(r_0, c_0) = \left\{ (r, c) \;\middle|\; \text{Route}_D(r, c) \to (r_0, c_0) \right\}
\end{equation}
The total catchment area $A_{\text{catchment}}$ (in hectares) is the sum of grid cell areas within the delineated polygon boundary.

\subsection{Rainfall Data Integration and Runoff Yield}
Historical 10-year monthly precipitation time series are queried from the Open-Meteo Archive API for the selected location's centroid. Annual rainfall $P$ (in mm) is aggregated. Direct surface runoff volume is modeled using the USDA Soil Conservation Service Curve Number (SCS-CN) method:
\begin{equation}
S = \frac{25400}{CN} - 254 \quad (\text{Potential Maximum Soil Retention in mm})
\end{equation}
\begin{equation}
I_a = 0.2 \cdot S \quad (\text{Initial Abstraction in mm})
\end{equation}
\begin{equation}
Q = \begin{cases} 
  \dfrac{(P - I_a)^2}{P - I_a + S} & \text{if } P > I_a \\
  0 & \text{if } P \le I_a 
\end{cases} \quad (\text{Direct Runoff Depth in mm})
\end{equation}
Annual harvestable runoff volume $V_{\text{runoff}}$ (in $\text{m}^3$) across catchment area $A_{\text{catchment}}$ (ha) is:
\begin{equation}
V_{\text{runoff}} = Q \cdot A_{\text{catchment}} \cdot 10
\end{equation}

Pond dimensions are optimized using a 3D inverted trapezoidal frustum geometry:
\begin{equation}
V_{\text{pond}} = \frac{d}{3} \left( A_{\text{top}} + A_{\text{bottom}} + \sqrt{A_{\text{top}} \cdot A_{\text{bottom}}} \right)
\end{equation}
where side slope $z = 1.5$ ($1.5:1$ horizontal to vertical ratio), freeboard $F = +0.5\text{ m}$, and storage depth $d$ is constrained between $1.5\text{ m}$ and $4.0\text{ m}$.

\subsection{Frontend and Visualization}
The single-page web UI (`frontend/index.html`) features a full-screen Leaflet.js interactive map with dynamic tile layer switching (Esri Satellite vs. OpenStreetMap), drawing controls (Lasso freehand draw, bounding rectangle), location search with auto-complete dropdown, and a 3-tab sidebar:
\begin{enumerate}
    \item \textbf{Draw \& Area Tab}: Input location, choose drawing tool, fetch boundary, set rainfall slider.
    \item \textbf{Results Overview Tab}: Display harvestable runoff volume, catchment area, terrain slope, and cache status badge.
    \item \textbf{Pond Design Tab}: Displays recommended excavation depth, top/bottom length and width, embankment volume, and earthwork excavation specs.
\end{enumerate}

\subsection{Database and Storage}
The system uses a 2-tier caching layer. High-frequency queries are hashed by coordinate/polygon bounds (`polygon_hash`) and stored in a Supabase PostgreSQL table (`analysis_cache`). If Supabase is unreachable, the system degrades gracefully to an in-memory Python dictionary cache, ensuring uninterrupted service.

The three most significant engineering design decisions were:
\begin{enumerate}[leftmargin=*]
    \item \textbf{Nginx Load Balancer with \texttt{least\_conn} Routing}: DEM grid interpolation and D8 flow routing are computationally heavy matrix operations. Placing Nginx on VM1 with \texttt{least\_conn} ensures incoming map queries are routed to whichever worker VM currently has the lightest CPU load.
    \item \textbf{Two-Level Hybrid Caching}: By combining fast in-memory LRU dictionaries with persistent Supabase PostgreSQL storage, duplicate queries for popular villages bypass expensive GIS processing entirely.
    \item \textbf{Decoupled Modular Monolith Architecture}: Choosing a modular monolith over separate microservices eliminated inter-service network latency while allowing clean code separation between geocoding, terrain modeling, and API routing.
\end{enumerate}

\section{Discussion and Limitations}
\label{sec:discussion}
The AI-based Village Pond Planning System successfully automates complex hydrological calculations into a user-friendly web GIS platform. Key strengths include fast execution, load-balanced stability, and robust frustum geometry optimization.

However, several limitations exist:
\begin{enumerate}
    \item \textbf{DEM Spatial Resolution}: The 30m SRTM grid resolution smooths out micro-relief features under $30\text{ m}$. Incorporating 1m LiDAR DEMs would improve micro-catchment precision.
    \item \textbf{Soil Curve Number Uniformity}: The current model assumes a default Curve Number ($CN = 75$, AMC II) across the catchment. Spatially variable soil hydrologic group mapping (HSG A/B/C/D) would refine runoff estimates.
    \item \textbf{Static Rainfall Averages}: Long-term annual averages do not account for intra-seasonal dry spells or extreme 24-hour storm events.
\end{enumerate}
